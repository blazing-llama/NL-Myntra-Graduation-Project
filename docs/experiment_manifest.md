| EXP-002 | Codebook v2 category coverage (docs/codebook.md) | 613-item cleaned Play Store corpus (all three apps), keyword-scanned per barrier category | Manual keyword scan (`size/fit`, `price/discount`, `occasion/wear`, `quality/material`, `stock/available`, `forgot/later`, `wishlist/saved`) against full corpus, hand-reviewed for true positives vs. keyword-collision near-misses | Each of the 7 barrier categories would yield at least one genuine, corpus-grounded positive example | Only 2 of 7 categories (`quality_trust`, `availability_decay`) have a real positive example. 5 of 7 (`fit_size`, `price_certainty`, `occasion_styling`, `timing_forgetting`, `bookmark_not_intent` — the last only a borderline case) have **zero** clean positive examples; all keyword hits for those categories were post-purchase-logistics near-misses | Play Store alone cannot support a valid E1 accuracy measure for 5 of 7 categories — the exact categories the research questions (H1–H6) depend on most. Confirms and sharpens EXP-001's finding at the category level, not just the aggregate relevance rate. Do not freeze `docs/codebook.md` or write `agents/coding_agent_prompt.md` until positive examples for these 5 categories exist (expected from the Reddit corpus) and a second gold-set tranche (~20–30 items) is drawn from it and combined with the current 90 Play Store candidates into one full gold set. This is direct evidence for why the project needed multi-source triangulation (v2 Part A.3) rather than a single-source pilot | 2026-08-19 |
| EXP-003 | v2 Part D.4 — discovery-engine webhook must be live-tested, not just statically validated, before being treated as a working deliverable | `workflows/discovery-engine-webhook.json`, imported into a real local n8n 2.35.7 instance (self-hosted via npx, no Docker available) | CLI import + REST activation + live `curl POST` to the webhook, covering: real-relevant text, not-relevant text, missing text (400 path), and inspection of raw execution data / SQLite `webhook_entity` table when things silently failed | Workflow imports, activates, and the webhook responds correctly end-to-end on the first real n8n instance it touches | Found and fixed 4 real bugs before it worked: (1) missing workflow-root `id` blocked CLI import, (2) `tags` as plain strings blocked CLI import, (3) webhook node missing `webhookId` silently broke production webhook registration (a live in-place PATCH looked like it fixed it but corrupted the registered path — required full delete + clean re-import), (4) `$env.GROQ_API_KEY` access is blocked by n8n's default `N8N_BLOCK_ENV_ACCESS_IN_NODE=true` setting, meaning the workflow as designed would silently fail on any standard n8n Cloud/self-host instance without that explicitly disabled | All 4 fixes applied to `workflows/discovery-engine-webhook.json` (bugs 1–3) or documented as a required deploy-time setting (bug 4 — recommend switching to an n8n Credential instead of a raw env-var expression for the real public deployment). Confirmed working end-to-end: real classification, not-relevant classification, and the missing-text error path all returned correct responses. This validates the "never treat a workflow as working until live-tested" rule was the right call — every one of these 4 bugs was invisible to static validation | 2026-08-22 |
